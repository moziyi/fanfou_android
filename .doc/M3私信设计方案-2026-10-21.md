# M3 私信功能设计方案（2026-10-21）

> 状态：待用户确认后实现。承接 `.doc/饭否App设计方案-2026-10-16.md` 的 M3 里程碑：
> **会话列表 / 对话 / 发私信 / 未读**，验收标准「与网页端私信互通」。

---

## 1. 目标与范围

把底部导航「私信」Tab 从占位页变成可用功能：

1. **会话列表**：按对话聚合的私信入口（谁发的、最后一条说了什么、什么时候、有没有未读）。
2. **对话页**：与某个人的完整私信往来，自己的消息在右、对方在左，可继续发。
3. **未读**：会话列表上标出未读会话，Tab 上给出未读总数。

**不在本阶段范围**：私信的离线缓存、图片私信、撤回/删除私信、私信搜索。

---

## 2. 接口实测结论（2026-10-21 用真实 token 验证）

| 端点 | 方法 | 实测结果 |
|---|---|---|
| `/direct_messages/inbox.json` | GET | 200；扁平私信列表；参数 `count`(1–60)/`page`/`since_id`/`max_id`/`mode` |
| `/direct_messages/conversation_list.json` | GET | 200；**`[{dm:{...}, otherid, msg_num, new_conv}]`**；本账号实测 2 个会话（fanfou 18 条、zoeysa 1 条） |
| `/direct_messages/conversation.json` | GET | 200；参数 `id`(对方用户 id) 必选 + `count`/`page`/`max_id`；返回该对话的私信数组 |
| `/direct_messages/new.json` | POST | 表单 `user`(对方 id)、`text`(<140 字)、`in_reply_to_id` 可选 |

**私信对象字段**：`id, text, sender_id, recipient_id, created_at, sender_screen_name, recipient_screen_name, sender{user}, recipient{user}`。
`created_at` 是 `Mon Dec 04 15:12:55 +0000 2023` 这种英文日期串（与时间线同格式，复用现有相对时间解析）。

**待验证（需要测试账号）**：私信只能发给「也关注了我」的人（互为好友）——用测试账号「清若 corday」验证；
以及 `new_conv` 是否在读取会话后被服务端清零（决定未读标记是本地推导还是直接用服务端字段）。

## 3. 架构决策

### 3.1 缓存策略：私信不做 Room 缓存（与时间线不同）
时间线用 Room 做单一事实源，是因为它是「无限流 + 离线可读」。私信是**低频、强时效**的：

- 缓存要引入 `dm` / `dm_conversation` 两张表 + 会话与消息的一致性维护，成本与收益不匹配；
- 私信离线可读的价值很低（错过的私信在网页端也能看）。

**结论**：私信走**内存状态 + 每次进入页面拉取**，失败显示服务端原因与「重试」。
这与项目「简单直接优先」的取舍一致，也避免给 Room 引入第二套时间线机制。

### 3.2 未读的两条水位线
- **服务端字段优先**：会话列表直接给 `new_conv`（该会话有无未读）与 `msg_num`（消息数）。
  初版直接用 `new_conv` 渲染未读点；读取会话后重新拉会话列表，若服务端已清零则未读点自然消失。
- **Tab 徽标**：`sum(new_conv)` —— 服务端给的是布尔标记而非数量，初版徽标显示「有未读的会话数」，
  而不是未读消息条数（服务端没给这个数）。若实测发现 `msg_num` 能区分，则改为消息数。

### 3.3 发送
- `POST direct_messages/new.json`，`user` = 对方 id，`text` = 内容（<140 字）。
- 带 `in_reply_to_id` = 会话里最后一条私信 id（服务端支持，可选）。
- 发送成功 → 把返回的 dm 追加到内存列表（服务端返回完整对象，无需再拉一次）。
- 发送失败 → 保留输入框内容 + Snackbar 显示服务端原因，**不乐观插入**（避免假消息）。

### 3.4 与现有代码的关系
- 复用 `StatusCard` 之外单独做 `DmBubble`：私信没有图片/转发/收藏概念，不需要复用消息卡。
- 复用 `PhotoUi`/`UserUi`? 用户头像复用 `UserUi.avatarUrl`。
- 导航：新增路由 `dm`（列表）与 `dm/{userId}`（会话）；会话页在 Scaffold 底部有输入框，
  与时间线 Tab 的 `NavigationBar` 互斥（`showChrome` 现有逻辑按 route 判断，新增两条路由即可）。

## 4. 界面设计

### 4.1 会话列表（`DmListScreen`）
```
┌──────────────────────────────┐
│  私信                          │  ← 顶栏
├──────────────────────────────┤
│ (头像) 清若        3分钟前   │  ← 昵称 + @handle
│         @corday      ●       │  ← 最后一条消息预览 + 未读点
│         捏咸鱼              │
├──────────────────────────────┤
│ (头像) 饭否        2023年    │
│         您的账户疑似有非法…  │
└──────────────────────────────┘
```
- 底部导航「私信」Tab 保留；Tab 徽标显示未读会话数。
- 下拉刷新 / 触底翻页（`page`）。

### 4.2 对话页（`DmConversationScreen`）
- 顶栏：返回 + 对方昵称（点击进对方主页）。
- 主体：气泡列表，自己的右对齐（主色容器），对方左对齐（surface 容器），显示相对时间。
- 底部：输入框 + 发送按钮；空内容禁用发送；超过 140 字禁用并提示。
- 「对方需要互相关注才能私信」这类服务端错误直接显示在 Snackbar。

### 4.3 入口
- 「我」页加一行「私信」→ 跳会话列表。
- 通知（若后续做私信通知）点开直达对应会话。

4. 导航接入 + 「我」页入口 + Tab 徽标。
5. 真机验证：会话列表渲染、进入会话、发送（用测试账号 corday）、与网页端互通核对。

## 7. 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 私信需要双向关注才能发送 | 部分用户发不出 | 直接展示服务端原因，并提示「需要对方也关注你」 |
| 服务端 `new_conv` 语义不明（读取是否清零） | 未读点不准 | 读取会话后重拉列表，以服务端返回为准；初版即可自洽 |
| 私信对象 `created_at` 是英文日期串 | 相对时间解析失败 | 复用时间线已有解析，解析失败则回退显示原始串 |

## 8. 实施与验证记录（2026-10-21）

### 端点行为（真机 + 直连 API 实测）
| 端点 | 结论 |
|---|---|
| `GET direct_messages/conversation_list.json` | 200；条目 `{dm:{…}, otherid, msg_num, new_conv}`；**`new_conv` 记的是「对方」的已读状态**（对方读完即变 false），不能当作自己的未读标记 |
| `GET direct_messages/conversation.json?id=` | 200；返回**从新到旧**（id 递减）；空会话返回 `[]` |
| `POST direct_messages/new.json` | 表单 `user`/`text`/`in_reply_to_id` 生效，200 并返回完整私信对象；**对方关注了我即可发**（对方是受保护账号、我未关注 TA 也发送成功） |
| 私信对象 | `{id, text, sender_id, recipient_id, created_at, sender_screen_name, recipient_screen_name, sender{user}, recipient{user}}`；`created_at` 与时间线同格式 |

### 实现中调整的设计
- **未读改为本地水位线**：服务端 `new_conv` 表达的是对方的已读状态，无法回答「我还没看什么」。改为
  `未读 = 最后一条消息来自对方 且 其 id ≠ 本地已读标记`，已读标记按会话存于 DataStore
  （`read_markers` JSON）；打开会话即写入标记，列表在 ON_RESUME 时刷新。
- **会话标题**：会话内消息可推出对方昵称/头像；空会话没有消息，改用 `users/show` 兜底。
- **发起新会话的入口**：用户主页头部增加「私信」按钮（受保护账号同样可见，是否可发由服务端裁决）。
- **轮询任务**（原 MentionWorker，改名 FanfouPollWorker）顺带刷新私信未读会话数，写入 DataStore 供 Tab 徽标使用。

### 验证结果
- 会话列表渲染（头像/昵称/摘要/时间/未读点）✓，下拉刷新 ✓
- 进入会话：自己右、对方左的气泡方向正确，时间正确 ✓
- 发送：200 + 气泡立即出现 + 输入框清空 ✓；**对方（测试账号 清若 corday）在网页端收到并回复** ✓
- 对方回复后：列表置顶 + 未读点 ✓，Tab 徽标 = 1 ✓；打开会话后未读点与徽标消失 ✓
- 单测：新增 `M3PayloadTest`（真实载荷解析 + 映射），全绿
