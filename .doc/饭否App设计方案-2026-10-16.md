## 0. 实测已确认的 API 事实（设计的地基）

| # | 事实 | 实测方式 | 对设计的影响 |
|---|------|---------|------------|
| 1 | `https://api.fanfou.com` 可用，API 服务存活 | curl 直连 | 全部走 HTTPS，无需明文流量豁免 |
| 2 | 无自定义 User-Agent → 网关返回 404 HTML | curl 默认 UA vs 自定义 UA 对照 | OkHttp 统一 Interceptor 注入 UA |
| 3 | OAuth 签名 base string 必须用 `http://` scheme | 401 响应回显 Expected basestring | 签名器硬编码此规则，黄金用例固化进单测 |
| 4 | 签名需含 `oauth_version=1.0`、`oauth_callback`，标准 RFC 5849 排序 | 真实 key 签名请求 200 成功 | 签名器参数集确定 |
| 5 | 你的 consumer key 有效 | request_token 返回 200 + token | 登录链路无阻塞 |
| 6 | 未认证/错签名返回 401 JSON `{"request":..,"error":..}` | curl 实测 | 统一错误模型可依赖此结构 |
| 7 | 分页：`since_id`(>) / `max_id`(≤) / `count` 1-60 / `page` | 文档 | 分页策略（§5） |
| 8 | status 内嵌完整 user、photo{imageurl,thumburl,largeurl}、rawid 可排序 | 文档示例 payload | 数据模型（§4） |
| 9 | 限流 1500 次/小时（登录用户） | 文档 | 刷新节流策略（§7.3） |
| 10 | `created_at` 格式 `"Wed Nov 09 07:15:21 +0000 2011"`（英文 locale） | 文档示例 | 专用 parser，locale 显式指定 |

**待真机验证项**（无法在本机验证，列为 M0 首个任务）：
- `fanfan://` custom scheme 回调是否被授权页支持。文档明示 callback URL 任意值可传，风险低；**fallback 已备好**：PIN 码（oob）流程，签名器完全复用。

## 1. UX 目标 → 技术措施（先定 UX，再推技术）

| UX 目标 | 技术措施 |
|---------|---------|
| 打开 app 秒出时间线，弱网/无网也能看 | Room 作单一数据源，UI 只订阅本地 Flow；网络刷新异步 upsert |
| 下拉刷新只取增量，不浪费流量 | `since_id` 增量刷新，新消息插入本地库 |
| 上滑看历史消息无限加载 | `max_id` 翻页 + LazyColumn 到底部触发 |
| 写消息中途退出不丢稿 | 草稿 Room 持久化，composer 关闭即存 |
-| 回复/转发保持上下文 | `in_reply_to_*` / `repost_status_id` 参数 + context_timeline 详情页 |
| @我和私信有红点、有系统通知 | WorkManager 周期轮询 `account/notification`，差值触发通知 |
| 图片列表省流量、点开高清 | 列表用 `thumburl`（t0），点开 `largeurl`（n0），Coil 三级缓存 |
| 深夜刷饭否不刺眼 | Material 3 动态深色 |
| 发出失败不静默丢失 | 发送失败 Snackbar + 重试；不做离线队列（见 §5.4 权衡） |

**明确不做**（个人 app，控制维护面）： Widget、多账号、平板布局、锁屏快发、wearOS、云同步。

| UI | Jetpack Compose + Material 3 | BOM 最新稳定 |
| 架构 | 单 Activity + Navigation Compose + UDF (ViewModel + StateFlow) | — |
| DI | Hilt | — |
| 网络 | OkHttp + Retrofit + kotlinx.serialization | — |
| 缓存 | Room | — |
| 偏好 | DataStore (Preferences) | — |

| 后台 | WorkManager | — |
| 构建 | Gradle KTS + version catalog | — |
| SDK | minSdk 26 / targetSdk 36 | 覆盖个人日常机型即可 |

### 2.2 权衡决策记录（ upfront trade-offs ）

**D1: 单模块 vs 多模块** → **单模块，多包分层**
- 多模块收益在团队协作/编译加速/复用强制边界；个人 app 无团队，模块边界用包结构 + 架构测试约束即可。
- 多模块成本：构建配置翻倍、导航/资源跨模块引用摩擦。**选单模块**，包结构见 §3。

**D2: Paging 3 vs 手写分页** → **手写（Room 单一真相源 + Flow）**
- Paging 3 的 RemoteMediator + Room 场景为通用库做了大量「任意位置插入/删除」的适配，复杂度高，调试难，且与「时间线 = 追加型列表」的真实形态不匹配。
- 饭否时间线只有两种操作：头部插入新消息（since_id）、尾部追加历史（max_id）。LazyColumn + `LaunchedEffect` 检测最后可见项触发 loadMore，代码量 ~50 行，行为完全可控。
- 代价：失去 Paging 的内存优化（列表过大）。缓解：各时间线本地保留上限 2000 条，超出裁剪（LRU by rawid）。

**D3: Retrofit vs Ktor Client** → **Retrofit + OkHttp**
- OAuth 1.0a 签名是「给每个请求改写 header」的需求，OkHttp Interceptor 是最自然落点（签名器对上层完全透明）。
- Retrofit + kotlinx.serialization converter 成熟组合，社区资料多。

**D4: token 存储** → **DataStore 明文（app 私有目录）**
- 候选：EncryptedSharedPreferences（官方已标 deprecated 方向）、Keystore 手动加密（AES key 管理 + 备份恢复坑）。
- OAuth access token 威胁模型：需物理 root 或 adb backup（debug 才可）。个人 app + Android 私有目录沙箱已足够；引入 Keystore 换来的是备份迁移不可恢复的风险。**选明文 DataStore**，登出即删。

**D5: 离线发送队列 vs 失败即报** → **失败即报 + 重试按钮**
- 离线队列需要：持久化 pending 操作、幂等去重（饭否 API 无 client_id 幂等参数）、冲突合并——复杂度远超个人 app 收益。common path 是「有网刷饭否」。失败 Snackbar 重试已覆盖 99% 场景。

**D6: 通知轮询周期** → **WorkManager 30 分钟（充电/不限电均可）**
- 1500 次/时限额下，每 30 分钟 1 次 `account/notification` 年消耗可忽略。 exempted battery optimization 不申请（国内 ROM 需用户手动，个人 app 让 WorkManager 常规调度即可，收不到就收不到）。

## 4. 数据模型 — 不可变原始数据原则

三层严格分离：

```
DTO (core.network.dto)      →  Room Entity (core.database)  →  UI Model (core.model)
API 返回的忠实快照，             rawJson 原文 + 常用查询列          纯展示视图对象，
1:1 字段，全 nullable            (id, rawid, userId, 时间戳索引)    从 DTO 派生
```

**核心原则：API 原始 JSON 不经加工落库（`raw_json` 列），查询列只为索引/排序。** 好处：
1. 文档 2012 年后未再更新，实际 payload 与文档必然有漂移（新增/缺失字段）——raw 留底意味着 schema 理解错了随时可以重放重解析，不丢数据；
2. DTO 解析失败不 crash：未知字段忽略，缺失字段 null，原始数据永远可回查（调试期直接看库里 JSON）。

### 4.1 关键实体

```kotlin
// StatusEntity —— 一切时间线的原子单位
@Entity(tableName = "status")
data class StatusEntity(
    @PrimaryKey val id: String,          // "UcIlC04F2pQ"
    val rawid: Long,                     // 排序用
    val rawJson: String,                 // 不可变原始数据
    val userId: String,                  // 索引：用户页时间线
    val createdAtEpoch: Long,            // 索引：排序兜底
)

// 时间线成员表 —— 同一条 status 可属于多条时间线，多对多
@Entity(tableName = "timeline_entry",
    primaryKeys = ["timelineType", "statusId"])
data class TimelineEntryEntity(
    val timelineType: String,            // "home" / "public" / "user:{id}" / "mentions" / "context:{id}"
    val statusId: String,
    val rawid: Long,                     // 排序
)

// UserEntity: 同构（id, rawJson, screenName 冗余列, updatedAt）
// DraftEntity: 草稿（text, inReplyToStatusId, repostStatusId, updatedAt）
// DmEntity / ConversationEntity: 私信同模式
```

Timeline UI 查询 = `timeline_entry JOIN status ORDER BY rawid DESC` → Flow，Room 自动推送变更。

### 4.2 时间与字段解析
- `created_at` 用 `DateTimeFormatter.ofPattern("EEE MMM dd HH:mm:ss ZZZZZ yyyy").withLocale(Locale.ENGLISH)`；文档示例均为 +0000，解析后转 epoch 存储，展示层转本地时区/相对时间。
- `source` 可能是 `"网页"` 纯文本也可能是 `<a href=..>xx</a>` HTML（文档两处示例不一致）→ 解析函数二者兼容：含 `<a` 则抽取文本+链接。
- 全部 DTO 字段 `= null` 默认值，`ignoreUnknownKeys = true`。

## 5. 仓库层与分页

### 5.1 TimelineRepository（读路径，以 home 为例）

```
UI (Flow<List<Status>>) ← Room (timeline_entry JOIN status)
                              ↑ upsert
refresh(): GET home_timeline?since_id={本地最新rawid对应id}&count=60
loadMore(): GET home_timeline?max_id={本地最老id}&count=60
```

- Room 是唯一真相源，UI 永不直接持网络结果。
- since_id 语义是「大于」、max_id 是「小于等于」——首次翻页用最老 id 即可，不用 -1 技巧。
- 拉回的 status 列表：status 表 upsert（rawJson 覆盖更新，新鲜数据替换旧缓存）+ timeline_entry 插入。同时把内嵌的 user 剥离存 user 表（用户页直接命中缓存）。

### 5.2 写路径（发消息/回复/转发/收藏/关注）

网络直调，成功后把返回的 status upsert 进对应时间线（发消息→插入 user:{自己} 头部 + home 头部；收藏→更新本地 favorited 字段需重写 rawJson 中 favorited 位……实现上：favorited 状态单独存本地覆盖列，见 5.3）。

### 5.3 本地状态覆盖（favorited / following）

`favorited` 是「相对当前登录用户」的 API 字段，本地操作后即时翻转比重新拉取体验好，但改 rawJson 违反不可变原则 → **overlay 表**：`(statusId, favoritedOverride: Boolean?)`，UI model 合并时应用。following 同理作用于 user。

### 5.4 失败处理
统一 `ApiResult<T>`（success / failure(code, error) / network），401 → 踢回登录页（token 失效唯一场景），其余 Snackbar。无离线队列（D5）。

## 6. 认证设计（OAuth 1.0a + 浏览器授权）

```
[LoginScreen]
  ① POST-like GET request_token (签名: consumer key, callback=fanfan://oauth/callback)
  ② Chrome Custom Tab → https://fanfou.com/oauth/authorize?oauth_token=..&oauth_callback=fanfan%3A%2F%2Foauth%2Fcallback
  ③ 用户在饭否页输入账号密码点「愿意」→ 302 fanfan://oauth/callback?oauth_token=..&oauth_verifier=..
  ④ CallbackActivity (launchMode=singleTask) 收 verifier
  ⑤ GET access_token (签名: consumer + request_token + verifier)
  ⑥ GET account/verify_credentials → 拿到自己 user 落库
  ⑦ DataStore 存 access token/secret → 进首页
```

- ② 若 custom scheme 被 authorize 页拒绝（M0 真机首验），一键切换 `oob` PIN 流程：展示 PIN 输入框，其余链路不变（签名器/access_token 步骤完全复用）。
- ⑤ access_token 请求 base string 同样用 `http://fanfou.com/oauth/access_token`。
- **签名器（core/network/auth/OAuth1Signer.kt）**：纯 Kotlin，无 Android 依赖，输入(method, httpUrl, params, tokenSecret) → Authorization header。两个实测怪癖内置：base string 强制 http scheme；参数集含 oauth_version。
- API 请求签名：token 阶段签 `http://api.fanfou.com/...`（同规则），OkHttp Interceptor 全局注入 UA + Authorization。

## 7. 页面与交互

### 7.1 导航结构
底部四 Tab：**首页**（home / 随便看看 两 tab）/ **@我** / **私信** / **我**；全局 FAB 快速发消息。

### 7.2 页面清单
| 页面 | 数据源 | 要点 |
|------|-------|------|
| LoginScreen | OAuth 流程 | 见 §6 |

## 10. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|------|-----|------|------|
| custom scheme 回调不被授权页支持 | 低（文档明示 callback 任意） | 登录链路变 PIN 流程 | M0 首验，PIN 已是既定 fallback，成本 1 个输入框 |
| 实际 payload 与 2012 文档漂移 | 高 | 个别字段 null | DTO 全 nullable + rawJson 留底可重放（§4） |
| 国内 ROM 杀后台致通知延迟 | 高（国内常态） | 仅影响通知及时性 | 接受；主动打开 app 时全量校准 |
| API 单点故障/未来关停 | 低（已存活 14+ 年） | 全 app | 个人项目，接受 |
| 明文 DataStore 存 token | 低 | token 泄露需 root | D4 已权衡，接受 |
