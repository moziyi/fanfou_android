# M2 设计方案：@我 + 通知 + 用户体系

- 日期：2026-10-20
- 状态：已批准，进入实施
- 前置：M1 已收口（时间线、发布/回复/转发、收藏、删除、图片）

## 1. 范围

| 模块 | 内容 |
|---|---|
| @我 | mentions 时间线、分页、下拉刷新、底部导航徽标、已读水位 |
| 通知 | 系统通知（作者 + 正文）、15 分钟轮询、通知权限、点击深链到详情 |
| 用户体系 | 用户页（资料 + 关注按钮 + 消息/关注/粉丝三个 Tab）、关注/取关、关注与粉丝列表 |
| 我 | 我的主页、我的关注、我的粉丝入口 |

验收（来自总体设计）：**别人 @ 你，30 分钟内通知栏可见**。

## 2. 实测事实（2026-10-20，本账号）

| 端点 | 行为 |
|---|---|
| `GET statuses/mentions.json` | 200；默认 20 条，`count` 上限 60；`since_id`/`max_id` 生效；返回完整 status（含 `rawid`、`user`、`in_reply_to_*`） |
| `GET account/notification.json` | 200 `{mentions, direct_messages, friend_requests}` |
| 未读语义 | **调用 `mentions` 会清零服务端 `mentions` 未读数**（实测 1 → 0）。阅读接口即标记已读 |
| `GET users/show.json?id=` | 200；`following`、`notifications`、`protected`、四项计数、`description` 完整 |
| `GET users/friends` / `users/followers` | 200；`count` 生效（3 → 3 条）；`page` 翻页无重叠 |
| `GET statuses/user_timeline.json?id=` | 200；他人时间线可用；含 `repost_status` |
| `friendships/create|destroy` | wiki 为表单 `id`；实施前先探针（收藏端点的文档风格曾是 no-op） |

## 3. 设计决策

### D1 未读水位：本地双水位线（DataStore）

- `readUpToMentionsRawid`：打开「@我」时推进到当前最新 `rawid` → 决定徽标
- `notifiedUpToMentionsRawid`：系统通知发出后推进 → 防止重复通知
- 比较用 `rawid`（单调递增的数字），不用 base62 的 `id`
- 徽标数 = `timeline_entry` 中 `timelineType='mentions' AND rawid > readUpTo` 的行数

**取舍**：后台为获取正文必须调用 `mentions`，会清掉网页端未读数。替代方案（只查 `account/notification` 发「N 条新提及」）可保留网页徽标但通知没有信息量。本项目选择**带正文的通知**（自用客户端）。

### D2 @我 复用现有表

`status` + `timeline_entry`，新增 `timelineType="mentions"`。不新增实体、无迁移、离线可读，与首页同构。

### D3 用户页不新增缓存表

打开页面时实时 `users/show`；失败时降级使用 `user.rawJson` 渲染基础头部，关注按钮禁用。避免过期 `following` 导致误操作。

### D4 关注/取关

乐观更新 + 失败回滚；成功后重新拉 `users/show` 同步计数。写端点风格先探针后实现。

### D5 通知

- WorkManager 周期任务，**15 分钟**（系统最小值），网络约束，Hilt Worker；未登录直接跳过
- 前台不额外轮询；打开「@我」或下拉时刷新
- Android 13+ 请求 `POST_NOTIFICATIONS`
- 通知内容：`作者：正文`（单行截断），多条同组折叠 + summary；点击进详情
- 风险：Doze 可能延后。真机灭屏实测延迟；若 >30 分钟，改用 `AlarmManager.setAndAllowWhileIdle`（非精确、免权限）

### D6 导航与交互

- 卡片头像/昵称 → 用户页；卡片其余区域 → 详情
- 用户页：返回、资料头、关注/取关、Tab「消息 / 关注 / 粉丝」
- 通知点击 → `MainActivity`（`EXTRA_STATUS_ID`）→ 详情；404（审核中/已删）静默提示
- 「我」页：我的主页、我的关注、我的粉丝、退出登录

### D7 分页

- mentions：`max_id` 游标（与首页一致）
- 关注/粉丝：`page` 递增（`count=30`），到底以空页为界

## 7. 实施与验证记录（2026-10-20）

### 端点行为（真机实测）
| 端点 | 结论 |
|---|---|
| `statuses/mentions.json` | 200；count 生效（30/页）；`since_id` 语义正确；**调用即清零服务端未读数**；**不包含自己 @ 自己的消息** |
| `account/notification.json` | 200 `{mentions, direct_messages, friend_requests}`；因读取 mentions 会清零，不作为徽标来源 |
| `users/show.json` | 200；`following`/`notifications`/四项计数齐全；**`notifications` 不反映我方已发出的待审申请** |
| `users/friends.json` / `users/followers.json` | 200；`count` 生效；`page` 翻页无重叠；对未关注的受保护账号返回 403「你没有通过这个用户的验证」 |
| `statuses/user_timeline.json` | 200；对未关注的受保护账号返回 403 |
| `friendships/create.json` | 表单 `id` 生效（非路径风格）；普通账号 200 且 `following=true`；**受保护账号 200 +「已向 X 发出关注请求，请等待确认」**，再次调用 403（申请无法用 API 撤销） |
| `friendships/destroy.json` | 200；未关注时 403「X 还不是你关注的人」 |

### 关键实现决策（实施中追加）
- 徽标数量 = Room 中 `timelineType='mentions' AND rawid > readUpTo` 的行数；**轮询任务也会把 mentions 写入 Room**，否则从未打开过「@我」时徽标恒为 0。
- Tab 选择属于界面状态，移入 `UserScreen`（`rememberSaveable`），ViewModel 只管数据；避免两处状态不一致。
- 列表加载失败必须**停止自动分页**（原实现会无限重试，Protected 账号下转圈不停）；失败时展示服务端原因 + 「重试」。
- 关注申请态：服务端 403「…发出关注请求…」→ 按钮切换为禁用的「已申请」。
- Debug 构建在「我」页提供「测试通知（Debug）」入口，用于验证通知渠道与点击跳转（发布构建不包含）。
