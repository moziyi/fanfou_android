# 删除推文功能设计方案 — 2026-10-20

## 目标
当前用户**自己的**推文详情页，顶栏右上角提供「⋯」菜单，菜单项「删除推文」，点击后删除当前推文。

## 交互
- 可见性：仅当详情页目标推文的 `user.id` 等于当前登录用户 `id` 时显示「⋯」按钮；他人的推文不显示。
- 点击「⋯」→ `DropdownMenu`，唯一菜单项「删除推文」（错误色，destructive）。
- 点击菜单项 → 直接删除（与用户指定流程一致，不额外弹确认框：两次显式点击已构成确认）。
- 成功：自动返回上一页（时间线）；Room 是数据源，列表中该条即时消失，无需手工刷新。
- 失败：停留在详情页，Snackbar 显示服务端原因（如「没有这条消息」）。
- 删除期间：菜单项禁用，防止重复提交。

## 数据与接口（已实证）
- API：`POST https://api.fanfou.com/statuses/destroy.json`，表单字段 `id`。2026-10-19 实测返回被删除的 status 对象；被审核持有的推文返回 `404 没有这条消息`（与其它端点一致）。
- OAuth 签名：走既有 `OAuthSigningInterceptor`（表单字段参与签名，已有 golden 测试覆盖）。
- 本地：删除成功后清理 Room 中该 status 的 `timeline_entry` 行、`status` 行、`favorite_override` 行。
  - 不物理级联删除引用它的回复：回复保留（服务端会将其显示为原贴已删除），`pruneOrphans` 的 `IS NOT NULL` 约束不变。
  - 数据库版本不变（纯数据操作，无 schema 变更）。

## 分层改动
| 层 | 改动 |
|---|---|
| `StatusesApi` | 新增 `destroy(@Field("id"))` |
| `StatusRepository` | 新增 `delete(statusId): Result<Unit>`：先远端成功，再本地清理（远端失败不删缓存） |
| `StatusDao` | 新增 `deleteStatus(id)` / `deleteTimelineEntries(id)` / `deleteFavoriteOverride(id)` |
| `DetailViewModel` | 注入 `TokenStore` 暴露 `selfUserId`；新增 `deleteStatus()` 与一次性 `deleted` 事件 |
| `DetailScreen` | TopAppBar `actions`：拥有者才显示「⋯」+ 菜单；`LaunchedEffect(deleted)` 返回 |

## 边界
- 当前用户 id 为空（历史 token 未存 self user）：不显示删除入口（保守）。
- 详情页目标是他人的回复/转帖：不显示。
- 删除后若从通知/深链再次进入该 id：正常显示「消息不可用」。

## 验证
1. 单测全量通过。
2. 真机：API 发一条测试嘟 → App 详情页「⋯」→「删除推文」→ 返回列表且该条消失 → 服务端 `user_timeline` 不再包含；他人推文详情页无「⋯」。

## 附：转发带图重复显示的修复（2026-10-21）

**现象**：转发的消息带图片时，引用区显示一张图，正文区又显示同一张图。

**根因（真机载荷实证）**：饭否转发一条带图的消息时，**同一张图在载荷里出现两次**——
顶层 `photo` 与嵌套 `repost_status.photo` 指向同一个 CDN 对象：

```
顶层 photo     : https://s3-img.meituan.net/.../5f_6630.jpg@200w_200h_1l.jpg
嵌套原帖 photo : https://s3-img.meituan.net/.../5f_6630.jpg@200w_200h_1l.jpg
```

正文被 140 字截断时（`showsRepostQuote == true`）引用区会画原帖（连同它的图），
而 `bodyPhoto` 又把顶层的 `photo` 画了一遍 → 同一张图出现两次。

**修法**：`StatusUi.bodyPhoto` 在引用区显示时，比对正文图片与引用图片是否同一 CDN 对象
（比较时忽略 `@` 后的尺寸指令），是则不再在正文重复绘制；用户自己给转发配的新图
（不同对象）仍与引用区并存。

**验证**：真机复现（引用区 + 正文区各一张）→ 修复后只剩引用区一张 ✓；
新增 `StatusUiPhotoTest` 5 例覆盖四种组合。
